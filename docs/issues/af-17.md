# AF-17: Terminal-only voice conversations and agent-requested spoken replies

## Outcome

From an existing native Claude Code or Codex terminal, the user can say/type “read that answer aloud,” “speak your replies until I tell you to stop,” and “stop speaking.” The agent uses Agentflow on the Mac. No dashboard, browser tab, web microphone permission, or UI button is required. Terminal microphone input is also available so the entire voice loop can stay in the terminal.

Speech is a transport for the same native agent. It must not replace the agent with another model, start a new conversation, prepend a voice persona, or turn user input into a peer-agent message.

## Current baseline — implemented, not completion evidence for this issue

- `agentflow speak --text ...`, stdin speech, and MCP `speak` already call the configured local TTS provider and macOS output device.
- The Agentflow MCP server is registered in both local CLI configurations. Running sessions may need native MCP refresh before newly registered tools become available; do not restart an active conversation automatically.
- `current_time` and `session_history` MCP tools expose actual time/timezone and a bounded native-history preview with recorded timestamps.
- `agentflow run codex|claude` provides a native terminal attached to one service-owned process.
- Terminal microphone capture, persistent per-session speech mode, natural-language mode controls, CLI setup/diagnostics, and the acceptance suite below are NOT all implemented.

## Scope and interfaces

Extend AF-14 (#14), AF-12 (#12), and session adapters AF-05/AF-06 (#5/#6). Keep the dashboard optional.

Proposed interfaces (acceptance targets, not claims of existing commands):

- MCP `speak`: read explicit text once; return only after playback completes or fails.
- MCP `set_voice_mode`: `off` or `replies`, scoped to an explicit native agent/session ID. MCP `stop_speech` stops that session's playback without stopping its native agent.
- CLI commands to install/check both MCP registrations, select/test providers, enable/disable/query session speech mode, capture/send a spoken terminal utterance, and interrupt playback. Final command names must be documented and covered by CLI tests.
- Typed terminal text, OS dictation, and terminal microphone STT all submit to the same native session. Entering speech mode does not change model, cwd, permissions, tools, or history.
- “Read that aloud” is one-shot. “Speak your replies until I tell you to stop” enables subsequent final-answer playback. “Stop speaking” disables it and stops pending audio. “Stop this turn” is a separate explicit native-agent cancellation action.

## TDD implementation sequence

1. Create failing acceptance tests keyed T01–T14 before their production changes. Record the actual red run and expected failure, not just a checklist saying tests were written.
2. Start with browser-free one-shot speech and MCP execution/error contracts. Use fake TTS and a fake player to avoid paid API requests in ordinary tests.
3. Add a session-scoped mode controller and native final-answer event fixtures. Prove one-shot vs persistent mode, exact text, event ordering, and no cross-session playback before adding natural-language tool controls.
4. Add interruption, duplicate events, reconnect, crash recovery, stale provider results, and concurrent sessions. Use a fake clock; do not assert wall-clock network latency in unit tests.
5. Add terminal capture behind a replaceable audio-device interface. Red-test silence, denial, cancel, exact transcript delivery, and stream release before using a physical microphone.
6. Implement the minimum passing behavior, then refactor with the focused suite green. Run affected contract/integration tests after each behavior; map every criterion to named evidence.
7. Execute opt-in live checks in disposable sessions for BOTH CLIs and real Deepgram STT/TTS. Never use the user's active work as a fixture. Leave provider/account/hardware-blocked criteria unchecked.

## Definition of done

All T01–T14 have linked passing evidence (or this issue remains open); initial red and final green results are recorded; no subjective “sounds natural,” “seamless,” or “works well” substitutes for an assertion. Store no API keys, personal conversation history, or captured user audio in test artifacts or GitHub. Never claim a mocked provider test proves live audio success.

## Non-goals

Changing native permission policy, silently approving tool actions, cloning voices, routing agent inference through a new model, or making a browser necessary for terminal speech. Selecting a speech provider does not select the coding agent's model provider.
